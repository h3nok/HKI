# Agentic Platform Feature Map

## Status

Short verdict: mixed. The non-dashboard platform is strong v1 software: chat, Knowledge Domains, scoped routing, review, validation, HKI runtime packages, and core services are implemented and usable. The remaining production-readiness work is concentrated in evidence depth, service-level conformance proof, connector hardening, analytics aggregation, release workflow, and public framework packaging.

This map intentionally excludes the admin dashboard details because those are covered in [docs/ADMIN_CONTROL_PLANE_DASHBOARD_DESIGN.md](ADMIN_CONTROL_PLANE_DASHBOARD_DESIGN.md).

## Scope

- Included: Agentic public routes, chat/runtime, Knowledge Domains, connectors, journey/gamification, HKI framework packages, Python services, deployment/testing surfaces, and non-dashboard admin control APIs that back those features.
- Excluded: Detailed admin dashboard UI inventory, archived Cloud Run-era plans, retired integration paths, and every low-level endpoint implementation detail.
- Primary users: platform viewers, knowledge operators, managers, admins, framework adopters, and service maintainers.
- Primary routes or entry points: `/`, `/engineering`, `/login`, `/chat`, `/welcome`, `/knowledge`, `/knowledge/create`, `/knowledge/join`, `/knowledge/request-access`, package imports from `@hki/runtime`, `@hki/conformance`, `@hki/sdk`, and service endpoints on ports 9501, 9508, 9509, and 9510.

## Access And Rollout

- Roles: `viewer`, `operator`, `manager`, and `admin` are enforced through route guards, tRPC procedures, and feature flag minimum roles.
- Feature flags: chat capabilities, Knowledge tabs, library views, validate/govern/activity sections, ingest controls, connector availability, and debug controls are centrally defined in [apps/agentic/shared/feature-flags.ts](../apps/agentic/shared/feature-flags.ts).
- Tenant/domain gates: runtime data paths should resolve a non-global `valueStreamId` and forward scoped request context; this is explicitly tested in Knowledge, chat, connectors, journey, gamification, and WebSocket scope tests.
- Environment gates: Python services depend on env configuration for DB, Redis, GCS, Pub/Sub, model gateway, optional Document AI, optional Neo4j, and auth toggles.
- Launch limits: Dashboard is v1-complete separately; non-dashboard gaps remain around release evidence, analytics persistence, connector maturity, and public package release discipline.

## Quality Bar

- Typecheck/lint: `pnpm --dir apps/agentic check` is the primary Agentic validation command and was passing before this map was created. Framework checks include `pnpm typecheck:hki-runtime`, `pnpm typecheck:hki-conformance`, and Python package lint commands in [package.json](../package.json).
- Unit tests: Agentic has focused coverage across chat, scope isolation, connectors, journey, gamification, admin, feature flags, knowledge review, launch readiness, eval suites, and auth.
- Integration/service tests: service-level Python tests are run with `AUTH_ENABLED=false pytest tests/ -x --tb=short`; broader service sweeps are documented in [docs/TESTING.md](TESTING.md).
- Browser/runtime checks: Knowledge UI changes should use `make kb-ui-e2e` or focused browser checks; chat and dashboard runtime checks should capture console warnings when visuals or streaming state changes.
- Docs: active docs are indexed in [docs/README.md](README.md); service READMEs are useful but need cleanup where they still mention retired local paths.
- Known residual risk: service-level HKI black-box proof is not yet packaged as one evidence bundle; connectors and analytics need more production-grade confidence; release workflow is not yet a complete promotion/rollback system.

Recommended order: start with P0, because it gives every later hardening task a shared safety harness. Then run P1 and P2 in parallel if capacity allows: lifecycle reliability protects the core Knowledge workflow, while connector hardening keeps the content supply fresh. P3 and P4 should begin as design/API work while P1/P2 implementation is underway, then become release blockers when the platform moves from internal reference to public framework preview.

## Recommendations

1. Highest-leverage fix: add a service-level HKI evidence suite that runs against Orchestrator, Knowledge API, Ingestion, and Agentic BFF with null, global, wildcard, cross-domain, and cross-org attempts, then package the results with `pnpm verify:hki-conformance`.
2. Next hardening step: close the Knowledge lifecycle gaps by adding job cleanup/DLQ visibility, release candidate promotion/rollback, and evidence export for review/publish decisions.
3. Future enhancement: prepare the framework public release by adding examples, API docs, package publish dry-run, generated feature-flag catalog, and a docs pass that removes stale local-path references from service READMEs.
